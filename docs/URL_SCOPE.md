# URL 진단 범위와 단계 표시

적용 버전: 2.2.0 · 변경일: 2026-11-03

## 입력 가능한 URL

서버 기본 주소와 경로 및 쿼리를 포함한 HTTP·HTTPS URL을 입력할 수 있습니다.

| 예시 | 동작 |
| --- | --- |
| `https://example.com` | 동일한 스킴·호스트·포트 안에서 탐색 |
| `https://example.com/app/` | 기본 선택에서는 `/app/`와 하위 경로만 탐색 |
| `https://example.com/app/items?page=2&tag=a&tag=b` | 입력 URL과 반복된 쿼리를 보존하여 먼저 요청 |
| `https://example.com/api/v1/user/profile?user_id=alice&lang=ko` | 직접 응답을 점검하며 식별자 검사에서 다른 매개변수 보존 |

**입력 경로와 하위 경로**가 기본 범위입니다. `/app`은 `/app` 및 `/app/items`를 포함하지만 `/application`과 `/outside`는 포함하지 않습니다. `/app/login`을 입력하면 형제 경로 `/app/admin`까지 자동 확장하지 않습니다. `/app/` 전체가 목적이라면 `/app/`를 입력하세요.

**같은 서버 전체**를 명시적으로 선택하면 입력 경로 바깥의 같은 서버 경로도 검사합니다. 스킴·호스트·포트가 달라지는 주소, 하위 도메인과 리다이렉트 목적지는 자동으로 범위에 넣지 않습니다.

입력 쿼리는 입력한 경로에만 사용합니다. 다른 발견 경로는 해당 링크에 실제 적힌 쿼리를 사용하며 입력 쿼리를 임의로 복제하지 않습니다. 상대 링크는 발견한 페이지 주소를 기준으로 해석하고, 탐색 요청은 최대 80개 URL로 제한합니다. 같은 경로의 서로 다른 쿼리는 공격 표면에서 별도 항목으로 보존합니다. OpenAPI에서 발견한 작업은 기존처럼 목록으로만 수집하며 자동 실행하지 않습니다.

입력 경로를 기준으로 고정 검사 경로를 구성하고, 발견된 사용자 식별자 매개변수·프로필·관리자 경로도 현재 범위 안에서 검사합니다. 모든 URL·매개변수의 취약점을 일반적으로 탐지하는 기능은 아닙니다. 로그인 폼 자동 처리나 다중 계정 권한 비교는 이번 변경에 포함하지 않습니다. URL에 `아이디:비밀번호@`를 넣는 방식은 계속 거부하며, `#` 이후의 화면 위치도 서버 요청 대상이 아니므로 제외합니다.

## 진단 완료 아래 다섯 문구의 역할

| 표시 | 실제 근거 |
| --- | --- |
| 연결 | 입력 URL의 최초 접속과 서버 오류 확인 |
| 표면 탐색 | `[Phase 1]` 경로·링크·폼·API 문서 수집 |
| 설정 점검 | `[Phase 2]` 보안 헤더·쿠키·CORS·디버그 검사 |
| 접근 제어 | `[Phase 3]` 제한된 객체 접근 검사 |
| 경로 분석 | `[Phase 4]` 수집 정보와 발견 항목의 연계 |

이 표시는 메뉴나 검사 성공 보증이 아니라 진행 위치 안내입니다. 단계 로그가 바뀌면 현재 표시가 바뀌며 가상의 진행률을 만들지 않습니다. 완료 후에도 전체 문구가 남던 동작을 바꾸어 **진단 중에만 표시**합니다. 완료·실패·중단 뒤에는 문구를 숨기고 결과 상태와 소요 시간을 표시합니다. 세부 활동 기록은 로그 화면에서 확인합니다.

## 2.5 JavaScript 라우트

`http://127.0.0.1:18912/#/search?q=...`처럼 #/ 또는 #!/로 시작하는 앱 라우트를 허용한다. fragment는 HTTP 경로로 검사하거나 다른 서버 경로에 붙이지 않으며 브라우저에만 전달한다. 일반 #section 위치는 계속 거부한다. 네트워크 경계는 # 앞의 출처·서버 경로를 기준으로 유지한다. 실제 렌더링된 링크·검색 제어에서도 앱의 라우트와 매개변수를 수집한다.
