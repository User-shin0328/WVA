# WVA 추가 진단 규칙 설계

작성일: 2026-11-03 · 기준 버전: 2.4.0

## 현재 적용한 내용과 다음 개발 범위

2.3.0에는 발견 항목의 한국어 문제 요약, 실제 확인 내용, 가능한 공격과 성립 조건, 판정 범위를 추가했다. 원문 증거는 접어서 제공하고 조치 절차는 단계별로 펼쳐 읽을 수 있다. 같은 설명을 JSON·Markdown·CSV 보고서에도 포함한다. 기존 취약점 탐지 조건과 위험도는 이번 화면 변경으로 바꾸지 않는다.

**아래 R01~R13 전체는 설계 상태다. R04와 일부 겹치는 제한적 JavaScript 패턴 탐지만 2.4에 포함했다.** 설계 문서가 있다는 사실을 지원 기능이나 테스트 통과로 표시하지 않는다. 각 규칙은 양성·음성·오류 사례와 요청 경계 테스트가 통과한 뒤 별도로 활성화한다.

현재 엔진은 일부 고정 경로와 발견 경로의 헤더·디버그 응답·객체 접근·수집 키를 검사한다. 다양한 실제 사이트에서는 응답 형식과 경로가 달라 놓칠 수 있다. 추가 규칙은 특정 경로명보다 실제 요청·응답 문맥과 대조 조건을 활용하도록 설계한다.

2.4 통합에는 발견된 동일 출처 JavaScript 최대 5개의 앞 1,000,000자에서 알려진 자격증명 패턴을 찾는 제한적 기능이 포함됐다. 증거 값은 일부 접두사와 `[REDACTED]`로 가린다. 실제 비밀 값 여부·유효 권한은 확인하지 않으므로 R04의 전체 문맥·대조 검사 완료로 기록하지 않는다. 별도의 TLS 점검은 정상 인증서 검증을 거쳐 만료까지 15일 이내인지 확인하며 로컬 루프백은 제외한다. 만료·신뢰 오류 우회나 전체 TLS 설정 감사 기능은 아니다.

## 1 먼저 추가할 공통 기반

### 검사 결과와 취약점 발견을 구분

각 검사는 아래 상태 중 하나를 반드시 기록한다. 네트워크 실패나 권한 부족을 취약점 0건 또는 안전으로 바꾸지 않는다.

| 상태 | 의미 | 발견 항목 표 처리 |
| --- | --- | --- |
| PASS | 정해진 요청과 판정 조건 안에서 문제가 관찰되지 않음 | 취약점 수에 포함하지 않음 |
| SIGNAL | 반사·에러·의심 설정 등 징후가 있으나 추가 조건 미확인 | 잠재 위험으로 구분 |
| CONFIRMED | 해당 규칙이 정의한 구체적인 동작을 재현 | 확인된 동작과 한계를 함께 표시 |
| ERROR | 연결·해석·시간 초과로 확인하지 못함 | 미확인 건수와 사유 표시 |
| SKIPPED | 범위·권한·예산·콘텐츠 조건 때문에 제외 | 제외 사유 표시 |
| NOT_RUN | 전제 조건이나 실행 기능이 준비되지 않음 | 미실행 표시 |

CONFIRMED는 서버 전체 침해를 뜻하지 않는다. 예를 들어 외부 URL을 Location 헤더에 넣는 동작, 지정한 테스트 객체를 다른 계정이 읽는 동작처럼 **무엇이 확인되었는지**가 규칙마다 다르다.

### 결과 데이터 계약

```json
{
  "rule_id": "WVA-R06",
  "rule_version": "1.0",
  "status": "SIGNAL",
  "request_ids": ["request-1", "request-2"],
  "target_url": "<실제 검사 URL>",
  "parameter": "<변경한 매개변수>",
  "observed_behavior": "<응답에서 관찰한 사실>",
  "attack_conditions": ["<확인된 조건>", "<아직 확인하지 않은 조건>"],
  "evidence": [{"kind": "response_excerpt", "redacted": true}],
  "confidence": "<판정 근거의 신뢰도>",
  "severity": "<조건과 영향에 따른 위험도>",
  "limitations": ["<미검증 범위>"],
  "remediation_steps": [],
  "verification": []
}
```

예시 계약이며 현재 저장 형식을 교체한 것은 아니다. 신뢰도와 위험도는 독립적으로 기록한다. CVSS를 제공할 때는 버전·벡터·계산 근거를 함께 저장하고, 근거가 없으면 정식 계산 점수처럼 표시하지 않는다. 같은 요청의 여러 신호는 규칙·메서드·정규화 URL·매개변수·관찰 종류를 기준으로 중복 제거한다.

### 요청과 증거 관리

- 모든 규칙은 공통 요청기를 사용한다. 기존 스킴·호스트·포트와 선택 경로 경계, GET·HEAD 제한, 위험 경로 차단을 우회하지 못하게 한다.
- 전체 진단 180초·개별 요청 5초 제한과 요청 예산 중 먼저 도달한 한계를 적용한다. 남은 검사는 미실행 또는 예산 제외로 기록한다. 예산 도달을 모든 검사 성공으로 처리하지 않는다.
- 기본 모드는 기존 응답 분석이다. 추가 요청 규칙은 모드와 예산을 별도로 표시한다. 다음 기본값은 후속 구현 제안으로, 동시 요청 1개·초당 최대 2회·진단 전체 200회·호스트 오류 3회 연속 시 중단을 시작점으로 삼는다.
- 각 응답의 분석 크기는 기본 1MiB, 증거 발췌는 2KiB 이하로 제한한다. 대형·압축·바이너리 응답은 분리 처리하고 잘린 응답은 그 사실을 표시한다.
- 키·토큰·쿠키·개인 식별정보는 UI, 로그와 모든 저장 형식에 같은 마스킹 정책을 적용한다. 원본 보관이 필요하면 별도 접근 통제와 보존 기간을 사용한다.
- 테스트 계정·테스트 객체·허용 매개변수는 사용자가 지정한 목록으로 제한한다. 무차별 식별자 추측이나 사용자 데이터 수집으로 범위를 넓히지 않는다.

## 3 규칙별 판정과 테스트 기준

### WVA-R01 응답 문맥을 반영한 보안 헤더

**입력:** URL, HTTP 상태, 콘텐츠 유형, CSP·HSTS·X-Frame-Options·X-Content-Type-Options 헤더와 정책 값.

HTML 문서에는 강제 CSP의 존재와 적용 범위를 검토한다. CSP가 없는 것과 script-src가 광범위한 것을 별도 신호로 분류한다. 클릭재킹 방어는 유효한 CSP frame-ancestors와 X-Frame-Options를 함께 평가한다. HSTS는 HTTPS 응답에서만 확인하고 보고 전용 CSP를 강제 정책으로 세지 않는다.

**오탐 제외:** JSON API의 CSP 누락을 HTML 페이지와 같은 위험도로 일괄 보고하지 않는다. CSP 누락을 XSS 성공으로, HSTS 누락을 HTTPS 암호화 실패로 표현하지 않는다. 정상 frame-ancestors가 있으면 X-Frame-Options 누락만으로 중복 보고하지 않는다.

**증거:** 실제 콘텐츠 유형과 해당 헤더·지시어, 비교 기준. **테스트:** 보호된 HTML은 PASS, CSP 없는 HTML은 설정 문제, JSON API는 HTML 전용 규칙 SKIPPED, 보고 전용 정책은 강제 적용과 구분되어야 한다.

### WVA-R02 인증 쿠키 보호 속성

**입력:** Set-Cookie를 값 없이 분해한 이름·속성·범위, 명시적으로 지정한 인증 쿠키 목록.

Secure·HttpOnly·SameSite를 각각 검사하고 누락된 속성을 정확히 기록한다. SameSite=None의 Secure 요구 조건도 별도 확인한다. 쿠키 이름 추정만으로 인증 쿠키를 확정하지 않는다.

**오탐 제외:** JavaScript가 읽도록 설계한 비인증 환경설정·CSRF 토큰 쿠키를 세션 탈취로 단정하지 않는다. SameSite 누락 하나만으로 CSRF 성공을 보고하지 않는다.

**증거:** 쿠키 값은 제거하고 이름과 실제 속성만 저장한다. **테스트:** 안전한 세션 쿠키는 PASS, 속성별 누락은 각각 재현, 일반 설정 쿠키는 낮은 신호 또는 정책상 제외, 모든 출력에서 원문 쿠키 값이 없어야 한다.

### WVA-R03 상세 오류와 디버그 정보

**입력:** 수집한 텍스트·JSON 응답. 추가 오류 유발 요청은 기본으로 하지 않는다.

스택 프레임·파일 경로·예외 형식·프레임워크 디버그 구조 등 여러 근거가 같은 오류 문맥에 나타나면 상세 오류 노출로 보고한다. 제품명이나 버전 문자열 하나는 정보성 단서로만 남긴다.

**오탐 제외:** 개발 문서에 인용된 traceback 예제, 코드 블록, 보안 교육 자료와 동일한 문구를 구분한다. 500 상태만으로 정보 노출을 확정하지 않는다.

**증거:** 마스킹한 구조적 발췌와 일치한 분류. **테스트:** 실제 오류 구조 양성, 튜토리얼 음성, 빈 500 응답은 상세 노출 없음, 시간 초과는 ERROR여야 한다.

### WVA-R04 인증정보와 민감 필드 노출

**입력:** 현재 범위에서 이미 수집한 JSON·HTML·텍스트와 명시적인 민감 필드 정책.

키·토큰의 필드명, 값 형식, 응답 문맥을 조합한다. 실제 유효성 검증 없이 활성 자격증명으로 확정하지 않으며 임의 외부 서비스에 전송해 검사하지 않는다. 응답에 불필요한 개인 정보가 있는지는 해당 API의 허용 필드 정책과 비교한다.

**오탐 제외:** 샘플·마스킹 값, 공개 식별자, 문서 예시와 공개 키를 비밀 키로 혼동하지 않는다. 엔트로피나 secret이라는 필드명 하나만으로 심각도를 높이지 않는다.

**증거:** 값의 해시 식별자·유형·출처 요청 ID와 마스킹 위치. **테스트:** 실습 비밀 값 탐지, 예제 값 제외, 공개 키 제외, UI·JSON·Markdown·CSV·로그 전체의 원문 비밀 값 비노출을 확인한다.

### WVA-R05 CORS 출처 대조

**입력:** 기준 응답과 서로 다른 두 테스트 Origin을 사용한 응답. 규칙별 추가 요청 예산은 기본 3회다.

허용 정책상 승인되지 않은 출처가 반사되는지 대조하고 credentials 허용·응답 민감도·인증 조건을 따로 기록한다. 실제 사용자 인증정보는 등록된 테스트 세션에서만 사용한다. 브라우저에서 읽기까지 재현하지 않았다면 헤더 조건 확인으로 제한한다.

**오탐 제외:** 정확한 허용 목록, 공개 데이터의 와일드카드 허용, 브라우저에서 인증 응답 읽기를 허용하지 않는 조합을 구분한다. 쿠키 전송 가능성은 SameSite·브라우저의 제3자 쿠키 정책과 요청 문맥을 함께 평가한다.

**증거:** Origin·ACAO·ACAC와 인증정보 사용 여부, 프리플라이트 및 읽기 재현 여부. **테스트:** 허용 출처만 성공, 임의 출처 반사, 인증 비허용, 공개 응답, 브라우저 차단을 서로 다른 결과로 구분한다.

### WVA-R06 입력값 반사와 출력 문맥

**입력:** 발견된 읽기 요청과 사용자가 허용한 매개변수. 기본 추가 예산은 매개변수당 2회이며 전체 예산을 넘지 않는다.

실행 코드가 아닌 고유한 무해 표식을 한 매개변수에만 넣어 반사 여부를 확인한다. HTML 텍스트·속성·스크립트·JSON·URL 중 어느 문맥인지 기록하고 이스케이프된 표식도 구분한다. 결과는 입력값 반사 SIGNAL이며 XSS 확정으로 승격하지 않는다.

**오탐 제외:** 정상 검색어 표시, 안전하게 인코딩한 텍스트와 JSON 데이터를 취약점으로 일괄 처리하지 않는다. 원래부터 존재하는 문자열이 표식으로 오인되지 않게 기준 응답을 비교한다.

**증거:** 매개변수명, 요청 쌍, 반사 위치와 인코딩 상태. **테스트:** 반사·비반사·안전 인코딩·문맥별 응답을 구분하고 스크립트가 실행되지 않아야 한다. 실제 실행 확인은 R12에서 수행한다.

### WVA-R07 외부 URL 리다이렉트

**입력:** next·return·redirect 등의 실제 발견 매개변수와 사용자가 지정한 검사 목록. 추가 예산은 후보당 최대 2회다.

비밀 정보가 없는 소유 테스트 URL을 값으로 사용하고 외부 출처의 Location이 반환되는지 확인한다. 목적지로 따라가지 않는다. 현재 경계 밖 URL로의 이동을 요청기가 거부하는 정책도 유지한다.

**오탐 제외:** 고정된 정상 로그인 이동, 상대 경로, 정확한 출처 허용 목록을 구분한다. 외부 이동 자체가 원래 제품 기능이면 취약 여부는 정책 검토 대상으로 남긴다.

**증거:** 기준 요청·변형 요청·3xx 상태·정규화 Location. **테스트:** 외부 Location 반환과 허용 목록 거부를 구분하고, 테스트 목적지 서버에 실제 요청이 0회임을 확인한다.

### WVA-R08 민감 응답의 캐시 정책

**입력:** 명시적으로 개인화된 테스트 응답, Cache-Control·Vary·Age 등 캐시 관련 헤더.

인증된 민감 응답이 public 또는 s-maxage로 공유 저장을 명시적으로 허용하면 설정 위험 신호를 남긴다. 헤더만 확인한 상태와 실제 캐시에서 다른 계정의 응답이 반환된 상태를 구분한다. 공유 캐시를 오염시키는 검사는 기본으로 하지 않는다.

**오탐 제외:** 공개 상품 데이터, 정적 파일, 비민감 콘텐츠와 정책상 공개 API를 제외한다. no-store 부재 하나만으로 사용자 간 데이터 유출을 확정하지 않는다.

**증거:** 값이 제거된 개인화 근거와 캐시 헤더. **테스트:** public 민감 응답 양성 신호, 공개 파일 음성, no-store 민감 응답 PASS, 캐시 부재 환경은 실제 유출 NOT_RUN으로 구분한다.

### WVA-R09 계정 간 객체 접근 대조

**전제:** 소유권을 아는 테스트 계정 A·B와 각각의 읽기 전용 테스트 객체, 명시적인 공개·비공개 정책. 계정과 객체가 없으면 NOT_RUN이다.

A가 자신의 객체를 정상 조회하는 기준을 확보한 뒤 미인증 사용자와 B의 세션으로 같은 객체를 조회한다. HTTP 200뿐 아니라 객체 ID·소유자·민감 필드를 비교한다. 요청별 계정 컨텍스트와 객체 출처를 그래프에 연결한다. 기본 요청 예산은 객체당 4회다.

**오탐 제외:** 200 로그인 페이지, 빈 오류 객체, 공개 프로필, 역할상 허용된 공유 데이터와 캐시된 다른 응답을 구분한다. 형식이 비슷하거나 응답 길이가 같다는 이유만으로 소유권 위반을 확정하지 않는다.

**증거:** 계정 별칭·테스트 객체 별칭·허용 정책·응답 필드 비교. 원문 세션 토큰은 저장하지 않는다. **테스트:** 본인 성공·타인 거부·미인증 거부·의도적 공유·교차 계정 누출을 각각 확인한다.

### WVA-R10 역할별 관리 기능 접근

**전제:** 관리자와 일반 사용자 테스트 계정, 역할별로 허용한 읽기 API 목록. 실제 관리 작업의 변경·삭제 기능은 실행하지 않는다.

관리자의 정상 응답과 일반 사용자·미인증 요청을 대조한다. ADMIN이라는 필드나 URL의 admin 문자열만으로 관리 기능을 확정하지 않고, 허용 정책과 실제 보호 데이터의 일치를 확인한다. 기본 예산은 기능당 3회다.

**오탐 제외:** 공개 상태 페이지, 단순 역할 표시, 200 오류·로그인 페이지를 제외한다. 관리자 정보 조회 가능을 모든 관리 작업 권한으로 확대하지 않는다.

**증거:** 기능별 역할 정책과 마스킹한 응답 차이. **테스트:** 역할별 정상 허용, 일반 사용자에게 보호 정보 노출, 공통 오류 응답, 계정 미설정 NOT_RUN을 확인한다.

### WVA-R11 SQL 주입 의심 신호 대조

**전제:** 격리된 실습 또는 소유한 테스트 환경에서 선택 실행한다. 읽기 전용으로 허용한 매개변수만 사용하며 기본 추가 예산은 매개변수당 4회다.

기준 응답의 안정성을 먼저 확인한 뒤, 통제된 입력 변형에서 DB 오류 구조나 반복 가능한 조건 차이가 있는지 비교한다. 오류 문자열 한 번 또는 500 상태만으로 SQL 주입을 확정하지 않는다. 시간 지연·데이터 추출·쓰기·외부 통신을 유도하는 방식은 제외한다.

**오탐 제외:** WAF 차단, 입력 검증 에러, 무작위 응답, 로그인 만료와 문서에 포함된 DB 오류 예시를 구분한다. 원인이 특정되지 않으면 SIGNAL로 남긴다.

**증거:** 기준·변형 요청 ID, 재현 횟수, 마스킹한 DB 오류 구조와 응답 비교. **테스트:** 취약 실습 조회와 매개변수화된 정상 조회, 불안정 페이지, WAF 응답, 일반 예외를 각각 구분한다.

### WVA-R12 브라우저 기반 XSS 확인

**전제:** R06의 반사 신호, 격리된 브라우저 컨텍스트와 운영 페이지에 영향을 주지 않는 소유 테스트 환경. 저장형 입력과 인증 상태 변경 기능은 기본 대상에서 제외한다.

외부 전송이나 쿠키 읽기를 하지 않는 소유 표식의 실행 여부를 확인한다. 반사, HTML 해석, 스크립트 실행을 별도 상태로 남긴다. 브라우저의 모든 하위 요청에도 출처·경로·메서드·응답 크기 제한을 적용해야 한다. 이 경계를 구현하지 못하면 브라우저 규칙을 활성화하지 않는다.

**오탐 제외:** 표식이 텍스트·콘솔 메시지에만 나타나는 경우와 실제 해당 문서 컨텍스트에서 실행된 경우를 구분한다. CSP 차단을 실행 성공으로 세지 않는다.

**증거:** 실행 표식 ID·문서 출처·브라우저 판정 이벤트와 최소 스크린샷. **테스트:** 안전 출력, 취약 출력, CSP 차단, 다른 프레임, 네트워크 이탈 차단, 브라우저 종료·세션 격리를 확인한다.

### WVA-R13 경로 조작과 파일 접근 대조

**전제:** 소유자가 만든 무해한 테스트 파일과 예상 허용 디렉터리. 임의 운영체제 파일이나 실제 비밀 파일을 읽는 방식을 기본 검사로 사용하지 않는다.

파일 읽기 기능의 허용된 테스트 매개변수에서 기준 파일과 경계 밖 소유 테스트 파일의 접근 결과를 비교한다. 네트워크 URL 경계와 대상 서비스 내부의 파일 경계는 서로 다른 개념으로 기록한다. 기본 추가 예산은 후보당 3회다.

**오탐 제외:** 에러 메시지에 파일명이 인용된 경우, 같은 내용을 반환하는 공통 페이지, 응답 길이 차이만 있는 경우를 제외한다.

**증거:** 소유 테스트 파일 표식의 일치, 기준 요청과 비교 요청. **테스트:** 정상 허용·정상 거부·경계 밖 테스트 파일 노출·동일 오류 페이지·시간 초과를 구분한다.

## 4 연계 경로와 출시 기준

구현 시에는 `core/rules/contracts.py`의 결과 계약과 `core/http/requester.py`의 공통 요청기를 먼저 두는 구성을 제안한다. `rules/passive/`, `rules/probe/`, `rules/auth/`, `rules/browser/`로 실행 조건을 나누고, 레지스트리는 전제 조건을 만족하는 활성 규칙만 실행한다. 단위·통합 검증 자료는 `tests/fixtures/rules/`에 분리한다. 이 경로들은 제안 구조이며 현재 생성된 실행 모듈이 아니다. 새 결과는 현재의 `reporting/risk_context.py` 및 공통 상세 창으로 전달하되 관찰 사실은 규칙 결과에서 가져와야 한다.

경로는 단순히 user_id·api_key 유형만 맞아 연결하는 대신, 값의 비밀 원문을 드러내지 않는 식별자와 수집 요청·사용 요청·계정 컨텍스트를 연결해야 한다. 각 단계에는 확인된 조건과 추정 조건을 나누어 기록한다. R04의 의심 키가 유효성 확인 없이 관리자 권한으로 바로 연결되면 안 된다.

규칙별 출시 기준은 다음과 같다.

1. 양성·정상·모호·오류·미실행 사례를 포함한 로컬 정답 데이터가 있다.
2. 규칙을 켰을 때 실제 대상 요청의 출처·경로·메서드·속도·횟수·응답 크기 제한이 지켜진다.
3. 오탐·미탐을 각각 집계하며 학습용 예시와 검증용 예시를 분리한다. 통과 테스트 수를 탐지 정확도로 환산하지 않는다.
4. 결과마다 관찰 사실, 가능한 공격, 성립 조건, 미확인 범위와 수정 후 확인 방법이 모두 표시된다.
5. JSON·Markdown·CSV와 UI의 판정 수준 및 마스킹 결과가 일치한다.
6. 규칙 ID·버전·전제 조건·요청 예산을 문서화한 뒤 해당 규칙만 활성화한다. 미완성 규칙을 전체 검사 완료로 표시하지 않는다.
