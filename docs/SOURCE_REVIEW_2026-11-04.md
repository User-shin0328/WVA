### P1-1. 운영 안전 모드에서도 파일 업로드·메타데이터 SSRF 검사가 실행됨

- 위치: `agents/engine.py:81`, `agents/system_auditor.py:204`, `agents/system_auditor.py:306`, `core/http/requester.py:53`.
- 엔진은 모든 모드에서 SystemAuditor를 실행한다. 업로드와 POST SSRF 함수는 발견한 URL을 스스로 `allow_post()`에 등록한다. 따라서 공유 요청 경계는 명시적인 사용자 작업 승인과 검사기가 추가한 작업을 구별하지 못한다.
- 실제 반례: `mode=safe`에서 `/api/upload`로 multipart POST가 전송됐다. 업로드 파일명은 고정 `shell.php`이며 전송 후 정리·잔존 여부 확인이 없다.
- SSRF 후보에는 `169.254.169.254`가 기본 포함된다. 요청 자체는 대상 웹서버로 보내지만, 취약한 대상이 해당 주소에 추가 요청할 수 있다. 대상 원점 제한만으로 이 간접 요청을 통제할 수 없다.
- 보완: 읽기 모드의 기본 쓰기 요청 금지, 개별 규칙·대상·쓰기/정리 계약의 명시적 승인, 임의 표식의 고유 파일명, 정리 확인을 요청 경계에서 강제한다. SSRF는 통제된 수신기와 비밀정보를 요청하지 않는 고유 상관 표식을 기본으로 한다. 실제 자격증명·내부 파일 내용을 수집하는 기능은 별도 승인 범위로 둔다.
- 완료 기준: 안전 모드에서 업로드·POST SSRF 0건, 허용하지 않은 작업 0건, 승인한 실습 작업은 취소·시간초과 후에도 잔존 표식 0건.

### P1-2. 단순 문자열·입력 반사를 실행 증거로 확정함

- 명령어 삽입: `echo wva_canary`가 포함된 입력을 단순히 그대로 출력하는 서버도 실행된 것으로 판정한다. 고정 표식이 요청과 응답에 함께 있기 때문이다.

- 보완: 성공 문구는 SIGNAL로 제한한다. SQLi는 안정 기준과 조건 쌍, 명령어는 입력 반사만으로 생성되지 않는 실행 결과, SSRF는 고유 요청 상관관계, 업로드는 명시적 성공과 별도 조회·정리 결과를 대조한다. 단순 허용 확장자 문제와 코드 실행을 분리한다.

- 완료 기준: 다른 자격증명·세션의 잘못된 연결 0개, 입증하지 않은 SYSTEM 후조건 0개, 목표와 결과 권한 일치.

### P2-2. 빌드 정보와 과거 검증 결과가 현재 실행파일을 식별하지 못함

- 위치: `docs/BUILD_INFO.json:7`, `docs/BUILD_INFO.json:8`, `docs/BUILD_INFO.json:19`, `dashboard/server.py:30`, `packaging/build.ps1`.
- 최신 exe는 64,645,378 bytes / SHA-256 `73da7504...`이지만 BUILD_INFO는 이전 65,658,315 bytes / `9b664f61...`과 PASS·123개 기록을 유지한다. 기존 문서의 검증 수를 이번 바이너리의 근거로 사용할 수 없다.
- 기능이 바뀌었는데 버전/규칙셋은 여전히 2.5.0이며 규칙별 version도 고정 1.0이다. API 버전만으로 사용자가 구형/신형 실행파일을 구별하기 어렵다.
- 보완: 빌드 시 commit·규칙셋·의존성 잠금·해시 manifest를 생성하고 동일 바이너리에 대한 결과만 연결한다. 해시 불일치는 배포 실패로 처리한다. 실행파일은 GitHub Release 자산으로 관리하고 서명·보안 검사·지원 OS 기록을 추가한다.
- 완료 기준: 소스·실행파일·검증 결과의 식별자가 자동으로 일치하고, 이전 증거를 현재 검증으로 표시하지 않음.

### P2-3. 새 규칙의 테스트가 성공 문자열에 편향됨

- 위치: `tests/test_audit_consent_and_deep_mode.py:148`, `tests/test_audit_consent_and_deep_mode.py:198`, `tests/test_audit_consent_and_deep_mode.py:252`.
- 새 서버 규칙 테스트는 조건에 맞는 문자열을 반환하는 Mock을 중심으로 한다. 이름에 error-based가 있는 SQL 테스트도 실제 DB 오류 분석보다 성공 문구를 반환한다. 이는 정규식 배선 검증에는 유용하지만 취약점 재현과 정상 거부의 구분 근거가 되지 않는다.
- 테스트가 정리 작업 없는 R14 PASS와 개별 설정 강제 활성화를 기대하므로 잘못된 제품 동작을 고정할 수 있다. 저장소에 `.github` 워크플로 파일은 확인되지 않았다.
- 보완: 이번 9개 반례를 정상 음성/부분 실패 회귀로 편입하고 기대값을 제품 계약에 맞게 수정한다. 새 규칙마다 실제 동작하는 소유 실습 앱의 취약/방어 쌍과 격리된 제3자 앱 대조를 추가한다. Windows CI에서 소스·exe·UI와 해시 대조를 재현한다.
- 완료 기준: 규칙별 정상 거부·문구 반사·정적 설명문·WAF·시간초과·예산 소진·취소·정리 실패·인증 경계가 검사됨.

## 5. 추가 반례의 기대/실제 결과

| 반례 | 기대 | 실제 |
| --- | --- | --- |
| safe 모드의 업로드 거부 HTTP 200 | POST하지 않음. 거부 응답은 취약점 아님 | POST 전송, 업로드 CRITICAL 확정, system 후조건 |
| 명령어 입력의 단순 텍스트 반사 | 명령 실행 확정 없음 | COMMAND_INJECTION 발견 |
| 항상 같은 SQL 설명문 | 조건 차이 없음, 확정 없음 | SQL_INJECTION 발견 |
| 항상 같은 메타데이터 설명문 | SSRF 확정 없음 | SSRF 발견 |
| 저장 시나리오 없는 deep 정리 | NOT_RUN, tested=0 | PASS, tested=1, 자동 정리 검증 완료 |
| 동시 요청 5개 중 3개 연결 실패 | 오류 3개와 미완료 표시 | PASS, errors=0 |
| 서버 규칙 검사 후보 0개 | NOT_RUN, tested=0 | R16~R19 모두 PASS |
| 인증된 소유자의 정상 프로필만 접근 허용 | BOLA 확정 없음 | 미인증 BOLA로 기록 |
| consent 생략, 원격 deep, sql/browser false | 명시 동의 필요, 검사 설정·상한 보존 | HTTP 200, consent=True 기록, 검사 강제 활성화·최소 1000 요청 설정 |

마지막 반례는 API 작업을 대기 함수로 대체했으므로 외부 진단을 실제로 실행하지 않았다. 1000은 설정된 최대 요청 수이며 실제 1000회를 보냈다는 의미가 아니다. 위 반례의 모든 대상 응답은 검토용 가상 응답이다.

재현 명령은 저장소 루트 PowerShell에서 실행한다.

```powershell
& .\.venv\Scripts\python.exe -m pytest -q --junitxml=tests/artifacts/review-latest/pytest.xml
$env:PYTHONPATH = (Get-Location).Path
& .\.venv\Scripts\python.exe tests\artifacts\review-latest\reproduce.py
& .\.venv\Scripts\python.exe tests\artifacts\review-latest\exe_check.py
```

추가 스크립트와 원시 결과는 Git에서 제외된 로컬 검토 폴더에 있다. 재현 스크립트는 결함을 관찰하고 기록하는 용도이며 제품의 전체 수락 테스트를 대체하지 않는다.

## 7. 권장 보완 순서와 재평가 조건

1. **작업 통제부터 수정:** safe 모드 쓰기·민감 SSRF 차단, 명시 동의·개별 검사 설정·요청 한도 보존, 격리 미검증 표시.
2. **확정 판정의 근거 강화:** 고정 성공 문구 우회 제거, 입력 반사와 실제 실행 분리, 인증/소유권 대조, 근거 없는 system 후조건 제거.
3. **상태와 증거를 정합화:** 미실행/부분 실패/정리 실패 구분, 아티팩트 출처별 그래프, 버전·해시 manifest 일치.
4. **실제 동작으로 검증 확대:** 이번 반례의 자동 회귀화, 실제 취약/방어 실습 구현, 최신 source/exe/UI/제3자 앱 대조와 CI.
5. **운영 기능 추가:** 진단 프로필·테스트 계정 설정 복원, 요청량·시간 예산의 사용자 제어, 대상별 제외 경로, 재검증 이력, 로그 보관/삭제 정책, 실행파일 서명과 배포 이력.

P1 항목이 모두 해결되고 최신 바이너리로 양성·음성·부분 실패·취소·정리 검증이 통과하면 70~80점 수준의 실무 보조 도구로 재평가할 여지가 있다. 이는 수정 전의 예상이며 달성 점수가 아니다. 80점 이상을 주장하려면 다양한 인증 방식·환경·대상에서의 반복 결과, 오탐 검토, 운영 장애 및 배포 검증이 추가로 필요하다.

## 8. 검토 한계

- 최신 소스 전체 테스트와 내장 데모·통제된 반례를 확인했다. 운영 사이트, 실제 조직의 인증/역할 정책, 운영 DB, 외부 네트워크 격리는 검증하지 않았다.
- 신규 LFI·명령어·SSRF·업로드의 독립 실제 취약 앱 양성/음성 전체 벤치마크와 최신 exe 전체 UI 회귀는 이번에 수행하지 않았다.
- 모든 코드 경로에 대한 형식 검증, 의존성 취약점 전수 검사, 대규모 장시간 부하·다중 운영자 테스트는 수행하지 않았다. `pip check`는 알려진 보안 취약점 검사가 아니다.
- 최신 커밋의 제목에 OWASP 확장이 포함돼 있어도 전체 OWASP Top 10의 완전한 구현·정확도를 의미하지 않는다.
- 이 보고서는 최신화와 분석 결과다. 발견한 결함을 수정한 보고서가 아니며 원격 저장소에 새 커밋을 푸시하지 않았다.
