# WVA 2.7 진단 흐름 개선 및 검증 보고서

기준일: 2026-11-06. 이 문서는 이번 변경의 동작, 재현 순서, 기대 결과와 한계를 설명한다. 최종 실행파일 해시와 실제 검증 수는 `BUILD_INFO.json`, `../tests/TEST_RESULTS.md`에서 확인한다. 소스와 실행파일 검증은 구분한다.

## 1. 재진단을 구분하는 근거

이전 보고서와 현재 진단의 **정확한 대상 URL, 선택 범위, 규칙 버전, 검사 설정, 계정 인증 정보**가 같아야 비교한다. 현재 진단 ID와 다른 완료 보고서 중 완료 시각이 가장 최근인 기록을 선택한다. 복사한 파일의 수정 시각으로 순서를 정하지 않는다. 화면에는 비교한 진단 ID와 완료 시각, 비교 조건을 표시한다.

계정 별칭만 같은 다른 계정을 동일 조건으로 취급하지 않도록, 인증 정보는 로컬 비교 키를 사용하는 HMAC 식별값으로 대조한다. 비밀번호·토큰 원문은 비교 이력에 저장하지 않는다. 로컬 비교 키는 데이터 폴더의 `logs/comparison.key`에 보관한다. 키가 사라지거나 인증 토큰이 바뀌면 기존 결과와 비교되지 않을 수 있다. 2.6 이전 기록과 규칙 버전이 다른 기록도 기준으로 사용하지 않는다.

“이번에 미발견”은 이번 조건에서 발견되지 않았다는 의미다. 수정 완료나 취약점 부재의 증명이 아니다. 개별 SQL 재검증도 원래 매개변수·기준 값·참/거짓 조건 쌍을 반복 대조하며, 미재현을 “조치 완료”로 바꾸지 않는다. 미지원 유형은 개별 검증 미지원으로 표시한다.

## 2. 완료 후 등급 표시

기존에는 필수 검사의 미실행·판정 보류·오류가 있으면 등급을 숨겼다. 완료 후 **발견 기준 참고 등급**을 표시하고, 검사 완료 여부와 보류 항목은 별도로 표시하도록 변경했다. 참고 등급은 발견 건수 기반 수치이며 전체 사이트 안전 등급이 아니다. API의 `finding_grade`와 `grade`도 이 의미를 분리한다. 선택한 검사 전체의 조건이 충족되지 않으면 종합 판정은 계속 보류한다.

## 3. 화면과 계정 프로필

- 로컬 데모 실행 버튼을 제거했다. 내부 테스트용 데모 API는 기존 호환성을 위해 유지한다.
- 메뉴 “경로”를 “체인”으로 변경했다.
- 공격 그래프의 크기를 18px로 제한하던 전역 SVG 스타일 영향을 제거했다. 노드 280×120px, 제목 16px를 기준으로 가로 스크롤, 확대·축소, 화면 맞춤, 크게 보기를 제공한다. 단계 클릭·키보드 선택은 현재 화면에서 상세 창을 연다.
- 계정 프로필은 **선택 사항**인 JSON 파일이다. 미인증 진단에는 파일을 선택하지 않는다. 로그인 상태 검사는 테스트 계정의 쿠키·Authorization 토큰 또는 로그인 폼 정보를 넣은 파일을 선택한다. 화면에서 형식 예제를 다운로드할 수 있다. 예제 토큰을 실제 테스트 토큰으로 바꾸어야 한다.
- 계정 간 접근 제어 검사는 계정 두 개만 등록해 자동 확정하지 않는다. 객체 소유자, 거부 대상 계정, 보호할 응답 필드 등 기존 접근 제어 대조 시나리오도 명시해야 한다. 파일 내용은 이번 진단의 메모리에만 사용하고 브라우저 저장소에 보관하지 않는다.

## 4. SQL Injection 조건 대조 보완

발견한 GET 쿼리·폼·API 문서의 매개변수를 우선한다. 추가로 실제 시작 GET 엔드포인트에서 `id`, `user_id`, `product_id`, `q`, `search`, `keyword`를 제한적으로 확인한다. 화면의 식별자·검색 프리셋 또는 쉼표 입력으로 선택할 수 있다. 후보 기본 한도는 12개이며 설정 가능 범위는 1~24개다.

추정 매개변수는 두 정상 값에 대한 반응을 먼저 확인한다. 두 응답이 같아 입력 사용을 확인하지 못하면 SQL 대조 요청을 늘리지 않는다. 모든 후보가 이 이유로 제외되면 PASS가 아닌 NOT_RUN이다. 반응이 확인된 후보는 정상 기준의 안정성을 확인한 후 참/거짓 조건 쌍을 2회 대조한다. HTTP 500, DB 오류 문자열, 성공 문구 하나만으로 SQLi를 확정하지 않는다. 추정 매개변수는 XSS 검사 후보로 자동 사용하지 않는다.

이 기능은 임의의 경로를 만들어 검색하지 않으며 POST·JSON·GraphQL 입력을 포괄하지 않는다. 응답 차이가 없는 블라인드 SQLi는 놓칠 수 있다. 시간 기반 SQL 검사는 기존의 별도 명시된 로컬 시나리오 범위를 유지한다.

## 5. 중요 정보 노출 검사 추가

| 규칙 | 검사와 확인 근거 | 확인 범위 |

| R21 | `.env`의 복수 설정 필드와 실제 형태의 비밀 필드 | 미인증 반복 요청, 무관 경로 대조. 원문 값은 출력하지 않음 |
| R22 | `.git/HEAD`의 ref 형식과 `.git/config`의 Git 설정 형식 | 저장소 메타데이터 노출 확인. 저장소 전체 다운로드는 하지 않음 |

새 검사는 로그인 세션과 분리된 미인증 클라이언트로 수행하며 선택 범위와 공통 요청 예산을 따른다. HTML 공통 오류 페이지, 마스킹된 값, 예제 문자열, 접근 거부 응답을 실제 비밀 노출로 보고하지 않는다. 발견 시 HIGH로 분류하지만 서버 장악이나 노출 키의 유효성까지 입증한 것으로 해석하지 않는다. 새 유형의 개별 재검증은 미지원이며 전체 진단으로 다시 대조한다.

## 6. 순서별 재현과 기대 결과

프로젝트 루트 PowerShell에서 실행한다. 테스트 환경 설치는 `../tests/Setup-TestEnvironment.ps1`, 기존 전체 절차는 `../tests/TEST_GUIDE.md`를 따른다. 외부 사이트는 필요하지 않다.

1. `.\.venv\Scripts\python.exe -m tests.run_tests` 실행. 기대: 기능·반례 테스트 모두 PASS, 테스트 도중 소스 변경 없음. 원본은 `tests/artifacts/pytest.xml`, `functional-provenance.json`이다.
2. `.\.venv\Scripts\python.exe -m tests.run_ui_checks --workflow` 실행. 자체 SQLite 대상과 소스 대시보드를 임시 포트에서 시작하고 종료한다. 기대: 프로필 예제 다운로드, 대표 SQL 후보 탐지, 정보 노출 3종, SQL 수정 전/후 재검증, 재진단 기준 ID, 그래프 확대·상세 창·반응형 화면이 모두 동작한다.
3. `powershell -ExecutionPolicy Bypass -File .\packaging\build.ps1` 실행. 기대: 루트 `WVA.exe`와 새 소스/바이너리 해시 manifest 생성. 빌드 직후 검증 상태는 NOT_RUN이다.
4. `.\.venv\Scripts\python.exe -m tests.smoke_executable` 실행. 기대: 소스 없는 임시 폴더에서 실행파일 단독 기동, 별도 고정 기준 대상으로 진단·저장·중단·오류 처리 통과.
5. `.\.venv\Scripts\python.exe -m tests.run_ui_checks --exe` 및 `--exe --workflow` 실행. 기대: 기본 화면과 이번 개선 흐름 모두 PASS. 결과의 실행파일 해시가 현재 바이너리와 일치해야 한다.
6. `.\.venv\Scripts\python.exe packaging/build_manifest.py --verify` 실행. 기대: `VALID`. 같은 바이너리 검증 결과를 모아 `python -m tests.run_tests --report-only`로 결과보고서를 갱신한다.

워크플로 원본: `tests/artifacts/upgrade-2.7/browser/result.json`. 화면: 같은 폴더의 `chain-1440.png`, `chain-768.png`, `chain-390.png`, `settings-*.png`. 실패 시 실행 로그와 결과 JSON의 오류를 먼저 확인한다. 브라우저가 없으면 Edge/Chrome 또는 Playwright Chromium을 준비해야 한다. 실패·미실행 기록은 PASS에 합치지 않는다.

검증한 실행파일 SHA-256: `368604c1da0384ba4faff9fe9094c9644ff336cb24cfa1a30b51b3217941f39b` (65,731,911 bytes). 참고 기록은 같은 실행파일 해시로 연결했다. 기본 화면과 신규 작업 흐름은 서로 다른 검증이다. 서버·확장 대조 수에는 소스 검사도 포함되므로 모두 실행파일 단독 테스트라고 합산하지 않는다.

신규 UI 검사 첫 실행은 두 도움말을 같은 선택자로 찾는 테스트 코드 문제로 중단되었다. 로그인 검사 도움말로 선택 범위를 좁힌 뒤 19개를 재실행하여 통과했다. 최초 실패 기록은 `tests/artifacts/upgrade-2.7/workflow-initial-failure.json`에 보존했다. 해당 수정은 테스트 선택자만 바꿨으며 빌드한 앱 소스는 바꾸지 않았다.

디자인 보조 검사의 2개 경고는 기존 요청에 따른 위험도별 5색 차트와 작은 보조 데이터 글자다. 데스크톱·모바일 화면을 직접 확인했고 차트 색상과 기존 정보 밀도는 유지했다. Impeccable 정적 검사에는 상속 색상·외부 CSS 해석에 따른 대비 경고 38개, 대시 1개, 진행선 모션 1개가 남는다. 브라우저의 실제 화면 검사와 구분하며 접근성 인증 통과로 보고하지 않는다.

최종 수행 시각·개별 결과는 `../tests/TEST_RESULTS.md`와 `BUILD_INFO.json`에 기록한다. 로컬 HTTP/SQLite의 실제 취약·방어 동작을 확인한 결과이며 운영 사이트 정확도, 탐지율 또는 무오탐을 보증하지 않는다. 원래 사용자의 클릭형 실습 대상과 시작 스크립트는 유지하고, 고정 회귀 기준용 대상은 `tests/lab/baseline_target.py`로 분리했다.

추가 보완 대상은 POST/JSON·다단계 인증·복잡한 권한 모델, DBMS별 블라인드 주입 문맥, 더 많은 독립 취약 앱의 양성/음성 대조, 개별 노출 규칙 재검증이다. 운영 자격증명과 조직의 비밀 관리 체계를 연동한 장기 저장은 아직 구현하지 않았다. 로컬 데이터·비교 키의 보관 권한과 보고서 공개 범위는 운영 적용 시 함께 관리해야 한다.
